# Google OKF Migration Risk Register

This register captures Phase 0 migration risks. It is intentionally separate
from the detailed findings in
[`PHASE_00_BASELINE_AUDIT.md`](PHASE_00_BASELINE_AUDIT.md) and the path-level
reference map in [`LEGACY_REFERENCE_MAP.md`](LEGACY_REFERENCE_MAP.md).

Likelihood and impact describe migration risk, not security severity.

| ID | Risk | Evidence/context | Likelihood | Impact | Mitigation | Recommended phase |
| --- | --- | --- | --- | --- | --- | --- |
| OKF-MIG-001 | Accidental knowledge loss from deleting `okf/` and `okf-bootstrap/` | 339 legacy Markdown files, 50 diagrams, a source register, 14 bootstrap reports, and marker/owner-question registers contain architecture, API, database, security, Marketplace, operations, and historical reasoning | High | Critical | Keep both trees intact; build a per-document preservation map and verify claims against current evidence before deletion | Phase 1 — Inventory & Preservation Map |
| OKF-MIG-002 | Loss of provenance and evidence scope | Legacy `primary_sources`, `related_documents`, `source-register.md`, verification commits/dates, and uncertainty markers do not have a one-to-one Google field mapping | High | High | Preserve source identity, path scope, dates, markers, and claim context before designing `sources`/footnotes | Phase 1 |
| OKF-MIG-003 | Broken human/agent navigation after `index.yaml` removal | `README.md`, `okf/README.md`, handoff history, and 25 tracked files reference `index.yaml` or its registry semantics | High | High | Inventory every consumer, define replacement navigation, update links in one controlled phase, and validate all paths | Phases 1–3 |
| OKF-MIG-004 | Stale duplicated knowledge is migrated as current fact | Legacy records use historical verification commits/dates; current HEAD and dirty security worktree are newer, and `okf/maintenance/validation-report.md` is a historical snapshot | High | High | Re-check every retained claim against current source, migrations, tests, configuration, and current docs; preserve historical labels | Phase 1 |
| OKF-MIG-005 | Legacy schema survives under a new directory without semantic review | All legacy concepts lack the required Google `type`; custom fields could be mechanically renamed into a superficially conformant bundle | Medium | Critical | Require a claim-level mapping with evidence, target type rationale, and unresolved markers; do not use filename or category alone | Phases 1–2 |
| OKF-MIG-006 | Custom ID/path relationships are lost or duplicated | `okf_document_id`, index IDs, filenames, and Google path-based Concept IDs are separate identity systems | High | High | Compare every legacy ID to its file path and references; retain an explicit alias/extension only where justified | Phase 1 |
| OKF-MIG-007 | Historical claims are presented as verified current behavior | `okf-bootstrap/` includes old counts, old branch/HEAD details, proposed plans, and a historical statement that final `okf/` did not exist | Medium | High | Label historical-only material, rank evidence by the repository precedence rule, and re-verify before promotion | Phase 1 |
| OKF-MIG-008 | Google examples or reference tooling are treated as normative requirements | The official spec says the format is minimal and lists fixed taxonomy, runtime, storage, and schema replacement as non-goals | Medium | High | Use only `SPEC.md` for conformance; mark examples, reference agent, visualizer, and conventions as informative | Phase 0 baseline; all later phases |
| OKF-MIG-009 | Premature taxonomy or extension design overfits ZinharCMS | Legacy `category`, `phase`, entity/module/domain IDs, and 14 directory areas are project conventions; OKF does not define a fixed taxonomy | Medium | High | Inventory existing categories first; choose only descriptive types needed by consumers; keep project-specific fields optional and evidence-backed | Phase 1–2 |
| OKF-MIG-010 | Generated-versus-curated content becomes ambiguous | Legacy documents mix observed source facts, prescriptive workflow, inferred architecture, historical phases, and owner questions without Google `generated`/`verified` semantics | High | Medium | Separate authoring, verification, lifecycle, and freshness facts; preserve `observed`, `prescriptive`, `mixed`, and uncertainty meaning during mapping | Phase 1–2 |
| OKF-MIG-011 | Concept duplication between OKF, `docs/`, code, migrations, tests, and diagrams | `okf/README.md` explicitly links rather than replaces existing docs, while catalogs repeat route/module/domain facts | High | High | Map each claim to an authority and choose link-versus-curated-summary deliberately; do not copy whole phase records | Phase 1–3 |
| OKF-MIG-012 | Mermaid and other non-Markdown artifacts are mishandled | 50 `.mmd` files are indexed as legacy knowledge, but Google OKF defines concepts/reserved files as Markdown and does not define Mermaid semantics | Medium | Medium | Inventory diagrams separately, preserve source/traceability, and decide link/reference treatment before moving or deleting | Phase 1–2 |
| OKF-MIG-013 | Runtime/tooling coupling is assumed absent or introduced accidentally | Exact searches found no executable consumer, but human workflows, README links, handoff instructions, and custom validation assumptions exist | Low | High | Re-run exact source/script/CI searches before removal; run safe application/CI/documentation checks after navigation changes | Phase 3–4 |
| OKF-MIG-014 | Old and new bundles are mixed without a clear boundary | The repository currently calls the custom `okf/` tree OKF while the target is Google v0.2; both could coexist during migration | High | High | Name and document legacy versus target explicitly, keep a staged boundary, and prohibit claims that the old tree is v0.2 conformant | Phases 0–3 |
| OKF-MIG-015 | Current pre-existing worktree changes are overwritten or misattributed | Before Phase 0, 23 paths were modified and 7 untracked; two modified paths are inside `okf/` and include current security knowledge | High | Critical | Keep the captured baseline, never reset/clean/stage unrelated work, and separate Phase 0 diff from pre-existing changes | Throughout migration |
| OKF-MIG-016 | Frontmatter/path links are broken during conversion | Legacy relation arrays use mixed legacy-relative and document-relative conventions; `index.yaml` has its own path semantics | Medium | High | Preserve original link text in the inventory, resolve targets against the correct root, and validate Markdown/path-valued fields after each migration step | Phases 1–3 |
| OKF-MIG-017 | Optional Google features become accidental obligations | Attested Computation, trust signals, `index.md`, `log.md`, and `references/` are optional; adding them without a use case creates maintenance/runtime expectations | Medium | Medium | Add optional families only when a verified ZinharCMS consumer needs them; document omissions as deliberate | Phase 2–3 |
| OKF-MIG-018 | Unknown/owner-policy questions are flattened into false certainty | `okf-bootstrap/09-knowledge-gaps.md` and `12-owner-questions.md` record production topology, recovery, retention, ownership, API, Marketplace, and terminology gaps | High | High | Carry `UNKNOWN` and `NEEDS_OWNER_CONFIRMATION` forward; resolve only with source/policy evidence and record decisions separately | Phase 1 and governance follow-up |

## Highest-priority gate

No deletion or conversion should begin until OKF-MIG-001, 002, 003, 004, 005,
006, 014, and 015 have a reviewed evidence trail. The absence of runtime
coupling reduces application breakage risk, but it does not reduce the risk of
irreversible knowledge and navigation loss.
